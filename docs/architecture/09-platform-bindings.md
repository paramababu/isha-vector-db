# 9. Platform Binding Architecture

## 9.0 The C ABI: one contract, six consumers

Everything native goes through `crates/vdb-ffi`, which exports a C ABI and a checked-in
`include/vdb.h` generated by `cbindgen` (CI fails if the committed header differs from a fresh
generation — the header is the contract, so drift must be impossible).

Design rules:

```c
typedef struct vdb_db vdb_db;                 /* opaque */
typedef struct vdb_collection vdb_collection;
typedef struct vdb_snapshot vdb_snapshot;

typedef struct { uint32_t code; const char* message; const char* detail_json; } vdb_error;

int32_t vdb_open(const vdb_open_options* opts, vdb_db** out, vdb_error** err);
int32_t vdb_close(vdb_db* db, vdb_error** err);
int32_t vdb_collection_upsert(vdb_collection* c, const vdb_doc* doc, vdb_error** err);
int32_t vdb_collection_search(vdb_collection* c, const vdb_search_req* req,
                              vdb_search_res** out, vdb_error** err);
void    vdb_search_res_free(vdb_search_res*);
void    vdb_error_free(vdb_error*);
const char* vdb_version(void);
uint32_t    vdb_abi_version(void);
```

1. **Opaque handles only.** No struct internals cross the boundary except plain
   `{ptr, len}` slices and POD request structs whose layout is `#[repr(C)]` and version-tagged.
2. **Vectors are never copied at the boundary.** `const float* data; uint32_t dim` — the callee
   copies once, into the WAL. This is what makes JSI `ArrayBuffer` and Dart `Float32List` fast.
3. **Every function returns an `int32_t` code** and writes an out-param. Errors are heap-allocated
   `vdb_error` with a code, a human message, and a `detail_json` field carrying the structured
   context, freed by the caller. No thread-local last-error (it breaks with thread pools).
4. **Explicit `*_free` for everything allocated by the library.** Ownership documented per function.
5. **`catch_unwind` at every entry point.** A panic crossing the ABI is UB; converted to
   `VDB_ERR_INTERNAL`.
6. **`vdb_abi_version()`** lets a binding refuse a mismatched library instead of crashing —
   essential when an app ships a prebuilt `.so` and an SDK that were built at different times.
7. **Complex, non-hot-path inputs (filters, specs) are passed as CBOR/JSON blobs.** Modelling a
   recursive filter AST in C would need ~20 constructor functions per SDK; one encoder per SDK is
   far less code and far less to keep in sync. Hot paths (vectors, ids, results) stay binary.
8. **Blocking, synchronous.** Every binding wraps calls in its own platform's concurrency
   primitive. The library never spawns a thread.

`vdb_search_res` returns a contiguous array of `{id_ptr, id_len, score, distance, doc_ptr}` so a
binding can iterate without per-hit allocation.

Distributed as: `.a` static libs (iOS, Android), `.so` (Android, Linux), `.dylib`/`.a` (macOS),
`.dll` (Windows), plus `vdb.h`. Built per target triple by the per-platform scripts that exist
today — `scripts/build-xcframework.sh`, `scripts/build-android.sh`, `scripts/build-web.sh` — and
by CI;
a single `build-native.sh` covering every triple is planned and not written,
with `panic=abort`, `lto=fat`, `codegen-units=1`, `strip=symbols`, and `opt-level="z"` for mobile.

## 9.1 React Native

```text
TS API (@vdb/react-native)   [planned: re-export shared TypeScript types]
   ↓  synchronous calls for cheap ops, Promises for the rest
JSI HostObject (C++)  ── installed by a TurboModule at startup
   ↓  zero-copy: ArrayBuffer → const float*
vdb.h  →  libvdb.a / libvdb.so
```

- **JSI, not the legacy bridge.** The bridge JSON-serializes everything; a 768-float vector becomes
  a ~10 KB JSON array. For a batch insert of 10k vectors that is the entire cost of the operation.
  JSI hands the C++ layer the `ArrayBuffer` backing store directly.
- **A small TurboModule** exists purely to install the JSI bindings and to expose the platform's
  documents directory. All real calls go through the `HostObject`.
- **Threading:** writes and searches run on a dedicated C++ thread with a serial queue; results are
  delivered by invoking the RN `CallInvoker` back on the JS thread. Nothing heavy runs on the JS
  thread — a 40 ms search on the JS thread is three dropped frames.
- **Zero-copy on the way out** too: hit ids and scores are written into a preallocated
  `ArrayBuffer` the caller can reuse, with an object-array convenience API on top for ergonomics.
- **Memory:** `HostObject` destructors are tied to the JS GC, which is not deterministic. The API
  therefore exposes an explicit `db.close()` and the SDK warns (in dev builds) if a database is
  finalized without one.
- **New Architecture only** (RN ≥ 0.73). Supporting the old bridge would mean maintaining two
  transports for a library whose selling point is speed. Version support policy is documented.
- **Expo:** an Expo config plugin plus support for development builds. Expo Go cannot load custom
  native code; say so explicitly in the docs, because it will otherwise be the #1 issue filed.
- Worth evaluating: **Nitro Modules** for codegen'd JSI bindings, which would remove most of the
  hand-written C++. Decision deferred to implementation time (ADR-0011).

## 9.2 Flutter

```text
Dart API (package:vdb)
   ↓  Isolate.run for heavy calls
dart:ffi bindings generated by ffigen from vdb.h
   ↓
libvdb.so / libvdb.a (via CocoaPods on iOS, CMake on Android, per-platform on desktop)
```

- **FFI, not method channels.** Method channels serialize through the platform channel codec and
  hop threads; FFI is a direct call. For bulk vector data the difference is order-of-magnitude.
- **`ffigen`** generates the Dart bindings from the same `vdb.h`, so there is no hand-maintained
  second description of the ABI.
- **Isolates:** an FFI call blocks the calling isolate for its whole duration, which would freeze
  the UI. Heavy operations run in a background isolate. Because a `Pointer` cannot be shared across
  isolates safely as a Dart object, the SDK keeps a single long-lived worker isolate that owns the
  handle, and the main isolate talks to it over a `SendPort` request/response protocol. Vectors
  cross as `TransferableTypedData` (zero-copy transfer, not a copy).
- **`NativeFinalizer`** attached to the Dart handle wrapper guarantees the native database is
  closed even if the app forgets — with an explicit `close()` still being the documented path.
- Packaging: Android via `CMakeLists.txt` referencing prebuilt `.so` per ABI; iOS/macOS via a
  `.xcframework` in the podspec; Windows/Linux via CMake. `flutter_test` cannot load native
  libraries in the pure-Dart test runner, so SDK tests are integration tests on a device/emulator.

## 9.3 Android (native Kotlin)

```text
Kotlin API (com.vdb:vdb-android, AAR)
   ↓
JNI shim (thin C, ~400 lines, or the `jni` crate)
   ↓
libvdb.so  (arm64-v8a, armeabi-v7a, x86_64)
```

- The JNI layer contains **no logic** — it converts `jstring`/`FloatArray`/`ByteBuffer` to C types,
  calls the ABI, and maps `vdb_error` to a Kotlin sealed-class exception hierarchy.
- Vectors arrive as a **direct `ByteBuffer`** (`GetDirectBufferAddress` → zero copy) or a
  `FloatArray` (`GetPrimitiveArrayCritical`, with the critical section kept to a memcpy).
- Kotlin API is `suspend`-based over `Dispatchers.IO`; a `Closeable`/`use {}` shape for lifecycle.
- Built with `cargo-ndk`; 16 KB page size support (required for Android 15+ on some devices) is a
  linker flag we must set from day one, not discover later.
- Storage path comes from `context.filesDir` (or `noBackupFilesDir` — recommended in the docs,
  since an auto-backed-up half-consistent database restoring onto a new device is a support
  nightmare). ProGuard/R8 keep rules ship with the AAR.

## 9.4 iOS / macOS (native Swift)

```text
Swift API (SwiftPM + CocoaPods)
   ↓
C interop over vdb.h (module map; no Objective-C layer needed)
   ↓
Vdb.xcframework  (device arm64, simulator arm64+x86_64, macOS arm64+x86_64, Catalyst)
```

- **No Objective-C shim.** Swift imports C directly via a module map; ObjC would be a pointless
  extra hop. An ObjC-compatible facade can be added later if someone needs it from an ObjC codebase.
- Swift API: `async`/`await` over a serial `DispatchQueue`, `throws` with a `VdbError` enum, and
  `withUnsafeBufferPointer` on `[Float]` for zero-copy vectors.
- Static library, not dynamic — avoids dylib loading cost at launch and App Store framework rules.
- Built by `scripts/build-xcframework.sh` (`cargo build` per triple → `lipo` for the simulator
  slice → `xcodebuild -create-xcframework`).
- Storage in Application Support with `.isExcludedFromBackup` guidance, and a documented note about
  Data Protection: a file in the default protection class is **unreadable while the device is
  locked**, so a background task touching the database can fail with `EPERM`. The SDK exposes the
  protection class as a config option and the docs explain the trade-off — this is exactly the kind
  of platform detail that produces "randomly fails in the background" bug reports.
- Memory: iOS jetsam counts dirty mapped pages against the app's footprint. A brute-force scan over
  a 300 MB mmap'd file can inflate footprint enough to be killed. Mitigation: on Darwin, scan in
  chunks with `madvise(MADV_DONTNEED)` after each chunk, or use `pread` into a reusable buffer.
  The chunked-scan path is measured against the mmap path in benchmarks before choosing a default.

## 9.5 Node.js

```text
TypeScript API (@vdb/node)   [planned: shared types from sdk/typescript]
   ↓
napi-rs addon (N-API, ABI-stable across Node majors)
   ↓
vdb-core directly (no C ABI hop — napi-rs binds Rust to Node natively)
```

- **N-API**, so one prebuilt binary works across Node versions without recompiling per release.
- Prebuilt binaries published as optional dependencies (`@vdb/node-darwin-arm64`,
  `-linux-x64-gnu`, `-linux-arm64-musl`, `-win32-x64-msvc`, …), with a source build as fallback.
  No `node-gyp` in the happy path.
- Async operations run on the libuv threadpool via `AsyncTask`, so the event loop never blocks.
  Synchronous variants are offered for scripts and clearly marked.
- Vectors accepted as `Float32Array`; the underlying `ArrayBuffer` is borrowed for the call.
- Works in Electron (same N-API) and, with a caveat, in Bun; Deno via its N-API layer. Support
  status per runtime is a table in the docs, tested where feasible in CI.

## 9.6 Web / WASM

```text
Main thread:  @vdb/web  (TS façade, identical API surface to @vdb/node)
   ↓  Comlink-style RPC over postMessage (structured clone / transferable ArrayBuffers)
Dedicated Worker:  vdb-wasm (wasm-bindgen)  +  vdb-storage-opfs
   ↓
OPFS FileSystemSyncAccessHandle   (fallback: IndexedDB block store; last resort: in-memory)
```

**The storage evaluation, which the brief asks for explicitly:**

| Option | Verdict |
|---|---|
| **OPFS + `createSyncAccessHandle`** | **Primary.** The only browser API with synchronous positional read/write, which is what our `File` trait needs. Available in Chrome/Edge 108+, Safari 16.4+, Firefox 111+. Worker-only — which is fine, because we want the engine off the main thread anyway. |
| **IndexedDB** | **Fallback.** Async, key-value only. We emulate a block device (64 KiB blocks keyed by `(file, block_no)`) with a write-back cache. Works everywhere including older Safari and private-browsing modes where OPFS is restricted, at roughly 3–10× the latency. Worth having because "it doesn't work in Safari private mode" is otherwise a permanent support burden. |
| **`localStorage`** | Rejected: ~5 MB, synchronous on the main thread, string-only. |
| **WASM memory only** | Supported explicitly as an ephemeral mode (great for tests and demos), never as the default. |
| **File System Access API** (`showSaveFilePicker`) | Optional export/import of a database file. Requires a user gesture, so it cannot back the engine, but it is the right way to offer "download my database". |

**Browser limitations that must be stated plainly in the docs** (rather than discovered):

- **Memory ceiling.** wasm32 has a 4 GiB address space, and in practice browsers cap a tab's WASM
  heap well below that (~2 GiB, often less on mobile Safari). At 768 dims that is a hard ceiling
  around 1–2 M vectors even before overhead. `memory64` is not broadly available yet. The engine's
  chunked-scan path (never loading all vectors into WASM memory at once) is what makes larger
  datasets possible at all in the browser; OPFS reads stream into a reusable buffer.
- **No mmap.** `capabilities().mmap = false`; the scan uses buffered positional reads.
- **No real fsync.** OPFS `flush()` is best-effort; the browser and OS may reorder. `durable_sync
  = false`, and the WAL + dual-slot manifest still protect against *tab* crashes, which are the
  realistic failure mode. This is honestly reported in `DatabaseStats`, not glossed over.
- **Eviction.** OPFS is best-effort storage: the browser can delete it under pressure. The SDK
  calls `navigator.storage.persist()` and surfaces the result, and `estimate()` is exposed so an
  app can warn before hitting quota. **A browser database is a cache, not a system of record** —
  that sentence belongs in the web README.
- **Threads need COOP/COEP.** `SharedArrayBuffer` (and therefore wasm threads / parallel search)
  requires cross-origin isolation headers many sites cannot set. Default build is single-threaded;
  a `-mt` build is published separately for sites that can.
- **SIMD**: `simd128` is widely supported; ship a SIMD build with a non-SIMD fallback selected by
  feature detection at load time.
- **Bundle size.** Target < 400 KB gzipped for the WASM module; tracked in CI with a size budget
  that fails the build when exceeded.

## 9.7 API parity across SDKs

A shared sdk/typescript package (planned) would define the canonical API shape. A machine-readable API description
(a machine-readable `api.json` generated from the Rust public API — **planned, not built**) would drive:

- a **parity test** in CI asserting every SDK exposes every stable operation (or explicitly
  declares it unsupported with a reason);
- generated API-reference documentation per language, so the docs cannot drift from the code.

Each SDK adapts naming to its platform's conventions (`camelCase` in TS/Swift/Kotlin, `snake_case`
in Rust, Dart conventions in Flutter) but **never** changes semantics, argument order, error
classification, or defaults. Semantic divergence between SDKs is the fastest way to make a
cross-platform library untrustworthy.
